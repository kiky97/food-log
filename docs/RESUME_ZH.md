# Food Log：简历表述与面试证据

项目名称建议：**Food Log — AI 饮食记录与营养分析系统**。

技术栈：Java 17、Spring Boot 3.5、MongoDB、React 19、TypeScript、Gemini / AWS Bedrock、JUnit、Testcontainers、Vitest、JaCoCo、GitHub Actions。

以下表述应在你能解释实现细节、确认符合本人实际贡献后使用。每个方向挑 2–3 条即可，不必把三个版本重复放在一份简历里。

## Java 后端方向

- 基于 Spring Boot 和 MongoDB 实现饮食记录、食物确认与每日营养汇总，接入 **1,161 条瑞士 FSVO 官方食品数据、7 项营养指标**；通过可复现 ETL 排除 **55 条营养数据不完整记录**，保留源文件校验值与逐条排除原因。
- 建立 **160 条标注查询**的离线评估与精确匹配基线；修复类别词错误自动匹配问题，在其中 **60 条官方食品查询**上将错误自动接受数由 **5 次降至 2 次**、自动匹配精确率由 **88.9% 提升至 95.2%**，自动覆盖率由 **75% 调整为 70%**。
- 使用 JUnit、Mockito 与 Testcontainers 验证业务链路，**55 项常规后端测试通过**，包含 **10 项 MongoDB 集成测试**；JaCoCo 整体行覆盖率 **92.7%**、分支覆盖率 **78.4%**，通过 GitHub Actions 自动运行并归档证据。

## 全栈方向

- 使用 React、TypeScript 与 Spring Boot 构建饮食输入、候选食品搜索、人工确认及营养汇总流程，接入 **1,161 条官方食品数据**；未确认食品不计入营养总量，确认后重新计算并持久化。
- 在真实 Spring Boot + MongoDB 环境中完成桌面与手机 **2 种视口、6 项浏览器场景检查**，覆盖录入、未确认排除、搜索确认与刷新持久化；验证无页面横向溢出及未捕获浏览器异常。
- 完成 **10 项前端测试**及 TypeScript / Vite 生产构建，结合 **55 项常规后端测试**、覆盖率报告和可复现浏览器脚本，为跨端交互和数据一致性提供验证依据。

## AI 应用方向

- 通过统一接口支持 Gemini / AWS Bedrock 结构化食品实体抽取，将语言模型解析与确定性的食品匹配、份量换算、营养计算分离；以 mock 实现离线复现，并为不确定匹配提供人工确认流程。
- 构建样例与官方食品两套、共 **160 条标注查询**的检索评估，分别报告自动匹配精确率、覆盖率、候选召回率及延迟；在 **1,161 条官方食品库、60 条开发查询**上，决策正确率较精确匹配基线由 **66.7% 提升至 96.7%（+30 个百分点）**。
- 通过真实数据评估定位不充分描述的误匹配，在同一 60 条开发查询上将误自动接受由 **5 次减少至 2 次**；保留失败案例和复现实验，明确精确率提高伴随自动覆盖率下降的权衡。

## 数字应该怎样解释

| 数字 | 证据与准确含义 |
|---|---|
| 1,161 / 1,216 / 55 | 官方 Excel 的 Generic Foods 表，经七项营养字段完整性筛选后导入 1,161 条，排除 55 条；不是声称导入官方数据库全部食品 |
| 160 条查询 | 样例库 100 条 + 官方库 60 条；手工整理的开发/回归集，含直接名称、变体和合成负例，**不是独立生产测试集** |
| 95.2% 精确率 | 官方开发集中自动接受 42 条，40 条正确，2 条错误；不是全部查询准确率，也不是 LLM 抽取准确率 |
| 96.7% 决策正确率 | 60 条中 58 条符合预期，包括正例正确匹配和负例安全拒绝；包含人工确认决策 |
| +30 个百分点 | 同一官方开发集下，模糊匹配 58/60 对比精确名称/别名基线 40/60；不是线上用户效果提升 |
| 55 项后端测试 | 常规 Maven 运行共发现 56 项，55 项通过，1 项可选评估按设计跳过；评估另行运行并通过 |
| 92.7% / 78.4% | 全部后端业务代码的整体行/分支覆盖率，无项目级排除；未将可选评估运行计入覆盖率 |
| 6 项浏览器场景检查 | 每个视口 3 项流程，桌面与手机共 6 项；不能称为 6 个独立业务功能 |

性能数字见 [实测报告](evaluation/RESULTS.md)：只测单线程进程内匹配，不包括 HTTP、AI 推理和 MongoDB，不可改写为“接口 P95”“支持 XX 并发”或“线上 SLA”。不建议把本机毫秒数放进第一版简历，除非你准备解释硬件、预热、采样与测量边界。

## 面试需要准备的追问

1. 为什么不直接让 LLM 输出卡路里？解释营养值来自官方表，模型负责结构化解析，确定性代码计算；源数据缺失不等于零。
2. 为什么精确匹配基线精确率 100%，还使用模糊匹配？精确匹配漏掉拼写、词序变体；它在官方开发集自动覆盖率仅 33.3%，模糊匹配为 70%，但仍有错误，需要确认机制。
3. 95.2% 能代表真实用户吗？不能。该集参与了缺陷发现和规则修复，是开发回归证据；下一步应冻结版本后用独立人工标注的真实查询测试。
4. 哪些问题还没有解决？`bread → Breadcrumbs`、`cheese → Cheeseburger` 的词法前缀误判仍存在；份量缺少官方单件重量；无用户登录；真实模型调用与麦克风未做端到端验证。
5. 官方营养数据怎样接入？说明按列名映射、版本与计量基准检查、来源 SHA-256、`CH-` ID、防止空值变零、独立数据库、幂等启动种子与 CSV upsert。
